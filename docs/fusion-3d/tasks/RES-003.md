## Procedure

1. Read 02_catalogue_schema_and_completion.md in full. Define schemas for source profile, faction, entity, mechanic/capability, terrain feature, map theme, observation, conflicting datum, asset provenance, adaptation decision and completion record.
2. Represent stable IDs independently of display names. Add parent/base alias links, faction/mode/edition availability, spawn relationships, transform/deploy states, weapons/abilities/upgrades, prerequisite graphs including exclusions, and terrain-layer requirements.
3. Use explicit units and datum wrappers with evidence status, source locators and uncertainty. Unknown numeric values are null with resolution tasks; zero must mean a measured zero. Distinguish active, referenced, declared, unused, cancelled and unclassified definitions.
4. Build importers for the two supplied candidate inventories without marking them verified. Preserve raw records and paths, pin/hash metadata and classification decisions. Later-era path candidates require content parsing and inclusion-graph resolution before becoming object records.
5. Define validation for duplicate IDs, dangling references, impossible producer/prerequisite cycles, faction availability contradictions, missing source/profile IDs, asset provenance gaps, illegal completion transitions and transformation identity errors.
6. Create one illustrative non-final fixture from an observed TD raw definition and one linked-state fixture for a later-era candidate. The fixture must use evidence fields and unverified markers; it must not invent statistics or imply that two examples constitute a census.
7. Define the deterministic implementation fan-out input/output schemas. Use canonical stages SPEC, SIM, MODEL, RIG, ANIM, FX_AUDIO_UI, INTEGRATE and REVIEW, with reviewed sharing allowed. RES-003 owns canonical immutable identity serialization; rowUid is SHA256(identity) prefix16 with the full hash retained and collision failure. Task IDs are F3D-ENTITY-<rowUid>-<stage>-<part>. OPS-005 alone owns publication/upsert and real-ID mapping; ART-013 expands/validates asset stages only. Terrain and support-power records need their own appropriate stages.
8. Create a preflight tool that emits actionable validation errors and a coverage report by profile/faction/category/status. Include tests only for meaningful schema risks such as silently converting unknowns to zero, collapsing forms, or dropping exclusions.
9. Document schema migration and backward compatibility. Get approval from the engine, world/art and independent research reviewer before era intake starts using a frozen schema revision.

## Acceptance and negative checks

- Both supplied raw inventories import with their original candidate status and record counts intact.
- Validation fails deliberately invalid evidence, forms, dependencies and incomplete release records while accepting explicit unresolved research data.
- Schema contains every category in the full catalogue specification and distinguishes source-rule values from Fusion adaptations.
- Task template is self-contained and includes sources, profile, exact outputs, acceptance fixtures and escalation criteria.
- Every factual claim used by downstream implementation is traceable to a recorded source or repeatable observation; uncertainty is represented explicitly with owner and resolution action.
- The artefacts are machine-parseable where specified, use stable IDs, contain no unresolved placeholder text disguised as final data, and have an independent reviewer assigned.
- A clean handoff lists changed files, exact reference versions, unresolved blockers, dependent capability IDs, next tasks, and the checks actually performed. A blocked critical datum prevents its affected implementation from being released, without blocking unrelated research.

## Guardrails

- Treat this card as a bounded contract. Read the named context and dependency outputs first. If required evidence is missing, record a precise blocked datum and continue only with independent work; never fill a field with an assumed zero, a plausible remembered value, or another era's value.
- Preserve native Classic fidelity independently from source-era research profiles and the newly authored Fusion rules. A Fusion change is an explicit adaptation decision with rationale and acceptance tests, never a retroactive claim about the historical game.
- Cite each nontrivial historical statement or numeric datum to an exact manual page, immutable source path/line or symbol, or timestamped observation in an identified shipped build. Search snippets, fan wikis, source declarations and official announcement text cannot alone prove shipped behavior.
- Keep code licence, trademarks, audiovisual assets, music, voice, map files and gameplay research as separate provenance questions. Do not redistribute retail game files or copied art/audio in the repository; original homage assets or specifically permitted material need their own provenance record.
- Never treat a source file, object identifier, cosmetic variant, projectile, alternate state, unused definition or script-only asset as a unique playable unit without classification evidence. Keep conflicts and exclusions visible and justified.
- Do not change GitHub, Linear, live game configuration, billing, or other external services under this research card. Commit only the approved research deliverables in an isolated branch; the fleet supervisor owns integration and publication.
- Write factual conclusions, calculations, test setup, results and concise decision rationale. No private reasoning trace is required. Spend available analysis on the assigned bounded task; do not inflate output or exceed the context window merely to claim exhaustive thought.
